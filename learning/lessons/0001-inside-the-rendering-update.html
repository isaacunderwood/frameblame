Lesson 01 · Web performance

Inside the Rendering Update

You can now read every LoAF field off a real frame. This is the machinery those fields are measuring — and the reason two of them can read zero while the browser is doing a hundred milliseconds of work.

The question the diagram left open

In figure F1, three markers collapsed into 0.7 ms at the right-hand end of the frame: renderStart, styleAndLayoutStart and paintTime. Everything between them is what the browser does after your JavaScript finishes and before pixels exist.

That span has a name in the HTML standard — the update the rendering step of the event loop — and it is not one operation but eight, in a fixed order. Knowing the order is what lets you place any performance API on the timeline instead of memorising each one separately.

The eight steps, in order

Once per frame, after the current task finishes, the event loop runs these in sequence:

  1. Resizefires resize
  2. Scrollfires scroll
  3. Media queriesevaluates and fires
  4. Update animations, fire animation events
  5. Fire fullscreen events
  6. Run animation frame callbacksyour requestAnimationFrame
  7. Update intersection observationsfeeds IntersectionObserver
  8. Update the renderingdraws to the screen

Two consequences fall straight out of the ordering. Your requestAnimationFrame callback runs at step 6 — before intersection observations and before anything is drawn, which is exactly why it is the right place to mutate the DOM for an animation and the wrong place to measure the result. And IntersectionObserver reports at step 7, once per frame, which is why it can never fire more often than the display refreshes.

The part that is missing on purpose

The trap

Style and layout are not in the list. The HTML standard has no concept of style or layout computation at all: it assumes they are synchronously implied by DOM changes, which can happen at any point — including before step 1 of the sequence above.

This single omission explains two things that otherwise look like browser bugs.

Forced synchronous layout. Because layout is implied by DOM state rather than scheduled, reading a geometric property — offsetHeight, getBoundingClientRect() — forces the browser to compute it right there, inside your script. The cost lands in your call stack, not in the rendering update.

And the inverse. Style and layout performed while no script was running, before the rendering update, are counted by nothing. LoAF's styleDuration and layoutDuration measure only the work inside step 8.

What that looks like in real data

Ninety-three per cent of that frame is attributed to nothing, and the profiler confirms it is not idle: every sample in it had an empty JavaScript stack. The work was real style and layout, running outside the rendering update where no field counts it.

The proof

Change one line so the listener reads offsetHeight after the mutation, and the identical work moves inside the script — where LoAF names it exactly: forcedStyleAndLayoutDuration of 96–116 ms, split into 24–25 ms style and 72–91 ms layout. styleDuration and layoutDuration still read zero.

Check yourself

Answer before scrolling back. Retrieving it from memory is what makes it stick; recognising it on the page is not the same thing.

A frame spends 130 ms in style and layout, yet LoAF reports styleDuration: 0. Why?

Style and layout are implied by DOM changes and can run at any point. LoAF's styleDuration counts only step 8. Work done before the rendering update begins is counted by no field at all — which is why an explicit unattributed slice is not optional in an honest tool.

Where do requestAnimationFrame callbacks run in the eight steps?

Step 6, immediately before intersection observations at step 7 and the drawing at step 8. So a rAF callback is your last chance to mutate the DOM before this frame is drawn — and measuring layout inside one forces the very work you are trying to observe.

Why does the HTML standard not list style and layout among the rendering-update steps?

The spec assumes style and layout are synchronously implied by DOM changes, even before step 1. Engines add their own internal steps on top. This is the root cause of both forced synchronous layout and the unattributable frame.
